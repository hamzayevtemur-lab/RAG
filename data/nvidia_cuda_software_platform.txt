1. CUDA ARCHITECTURE OVERVIEW AND PROGRAMMING MODEL
================================================================================
CUDA (Compute Unified Device Architecture) is NVIDIA's proprietary parallel computing
platform and programming model, first released in June 2007 with CUDA Toolkit 1.0. As of
CUDA 12.4 (released February 2024), the platform supports C, C++, Fortran, Python, and
Julia programming languages with first-class compiler and runtime support.

1.1 Programming Model Fundamentals:
CUDA extends standard C++ with a small set of language extensions:
- __global__ functions (kernels): Executed on the GPU, callable from host CPU code.
- __device__ functions: Executed on the GPU, callable only from other device functions.
- __host__ functions: Executed on the CPU (default for all standard C++ functions).

The execution model is organized into a three-level hierarchy:
- Grid: A collection of thread blocks launched by a single kernel invocation.
- Thread Block (CTA - Cooperative Thread Array): A group of up to 1,024 threads that
  execute on a single SM and share fast on-chip shared memory (up to 228 KB on Hopper).
- Warp: The fundamental execution unit consisting of 32 threads that execute instructions
  in lockstep SIMT (Single Instruction, Multiple Thread) fashion.

For Hopper H100:
- Maximum threads per block: 1,024
- Maximum blocks per SM: 32 (reduced from 16 on Volta/Ampere due to larger SM resources)
- Maximum active warps per SM: 64 (2,048 threads)
- Maximum shared memory per SM: 228 KB (configurable split with L1 cache)
- Total L2 Cache: 50 MB (shared across all SMs)

1.2 Compute Capability Versioning:
Each GPU architecture has a compute capability version that determines available features:
Architecture        Compute Capability    Key Feature Additions
---------------------------------------------------------------------------
Pascal              6.0, 6.1             Unified memory, NVLink 1.0
Volta               7.0                  Tensor Cores (1st gen), independent thread scheduling
Turing              7.5                  RT Cores, INT8/INT4 Tensor Cores, mixed precision
Ampere              8.0, 8.6             TF32, structural sparsity, async copy
Hopper              9.0                  FP8 Tensor Cores, DPX, TMA, thread block clusters
Blackwell           10.0                 FP4 Tensor Cores, 2nd-gen Transformer Engine

2. CUDA COMPILATION AND EXECUTION PIPELINE
================================================================================
2.1 NVCC Compiler:
The NVIDIA CUDA Compiler (nvcc) follows a split-compilation model:
1. Host code (CPU) is forwarded to the system's C++ compiler (GCC, Clang, or MSVC).
2. Device code (GPU) is compiled first to PTX (Parallel Thread Execution) — an intermediate
   virtual instruction set architecture (ISA) — and then to SASS (Shader Assembly), the
   native binary instruction format for the target GPU architecture.
3. The fat binary (.cubin or embedded in the executable) can contain multiple SASS variants
   for different compute capabilities, plus PTX for forward compatibility with future GPUs.

2.2 Just-In-Time (JIT) Compilation:
When a CUDA application encounters a PTX kernel targeting a newer compute capability than the
compiled SASS, the CUDA driver's JIT compiler translates PTX to SASS at first launch. The
compiled SASS is cached in the user's compute cache directory for subsequent runs, eliminating
repeated JIT overhead. This forward-compatibility mechanism ensures that applications compiled
today will run on future GPU architectures without recompilation.

3. MEMORY HIERARCHY AND OPTIMIZATION STRATEGIES
================================================================================
Efficient memory access patterns are the single most important factor in achieving high
GPU utilization. The memory hierarchy from fastest to slowest:

Level               Size (H100)     Bandwidth          Latency (cycles)    Scope
----------------------------------------------------------------------------------
Registers           256 KB/SM       ~20 TB/s            1                  Per thread
Shared Memory       228 KB/SM       ~19.5 TB/s          ~25               Per block
L1 Cache            Shared w/ SMEM  ~15 TB/s            ~30               Per SM
L2 Cache            50 MB           ~12 TB/s            ~200              All SMs
HBM3 (Global Mem)   80 GB           3,350 GB/s          ~400-600          All SMs + Host
System Memory(CPU)  Up to 2 TB      ~200 GB/s (PCIe5)   10,000+           Host

3.1 Coalesced Memory Access:
Global memory transactions are served in 32-byte, 64-byte, or 128-byte sectors aligned to
their size. When all 32 threads in a warp access consecutive 4-byte (float) addresses, the
hardware coalesces these into a single 128-byte transaction. Misaligned or strided access
patterns generate multiple transactions per warp, wasting bandwidth by a factor of up to 32x.

3.2 Shared Memory Bank Conflicts:
Shared memory is organized into 32 banks (4 bytes wide each on Hopper). When multiple threads
in a warp access different addresses within the same bank, the accesses are serialized
(bank conflict). Optimal access patterns ensure that each thread accesses a different bank
or that all conflicting threads access the exact same address (broadcast).

3.3 Unified Memory and Managed Memory:
CUDA Unified Memory (cudaMallocManaged) provides a single address space accessible from both
CPU and GPU. The CUDA runtime automatically migrates pages between CPU and GPU memory on demand.
While convenient for prototyping, Unified Memory introduces page fault overhead and is not
recommended for latency-critical production inference workloads.

4.1 cuDNN (CUDA Deep Neural Network Library):
cuDNN version 9.0 (released with CUDA 12.4) provides highly optimized implementations for:
- Forward and backward convolution algorithms: implicit GEMM, FFT-based, Winograd (up to 4x
  faster than direct convolution for 3x3 kernels), and pre-computed transform algorithms.
- Multi-Head Attention (MHA): Fused implementation supporting variable-length sequences,
  causal masking, and dropout in a single kernel launch. Supports FlashAttention-2 algorithm
  with O(N) memory complexity instead of O(N^2) for the attention matrix.
- Normalization: Fused BatchNorm-ReLU, LayerNorm, RMSNorm, GroupNorm.
- Pooling: Max, average, and adaptive pooling with support for arbitrary window sizes.

Algorithm selection in cuDNN uses a heuristic system that profiles available algorithms on
first invocation and caches the optimal choice. Users can also use cudnnFindAlgorithm() for
explicit benchmarking across all available implementations.

4.2 NCCL (NVIDIA Collective Communications Library):
NCCL version 2.20 provides optimized multi-GPU and multi-node collective communication:
- AllReduce: Ring, tree, and recursive halving-doubling algorithms auto-selected based on
  message size and topology (NVLink vs. InfiniBand vs. PCIe).
- Bandwidth scaling: On an 8-GPU DGX H100 with NVLink, NCCL AllReduce achieves approximately
  430 GB/s effective bandwidth for message sizes above 256 MB, which is 96% of the theoretical
  NVSwitch bisection bandwidth.
- Multi-node scaling: NCCL supports RDMA (Remote Direct Memory Access) over InfiniBand and
  RoCE (RDMA over Converged Ethernet). With Quantum-2 InfiniBand, inter-node AllReduce latency
  for 1 MB messages is approximately 15 microseconds, compared to 85 microseconds over RoCE.

6. TRITON INFERENCE SERVER
================================================================================
NVIDIA Triton Inference Server is an open-source, production-grade serving platform that
supports deploying AI models from any framework (PyTorch, TensorFlow, TensorRT, ONNX,
Python) on any GPU or CPU infrastructure.

6.1 Core Features:
- Dynamic Batching: Automatically combines individual inference requests arriving within a
  configurable time window (e.g., 50ms) into a single batched execution for higher throughput.
- Model Ensemble: Chain multiple models (e.g., tokenizer -> encoder -> decoder -> detokenizer)
  into a directed acyclic graph (DAG) pipeline within Triton.
- Concurrent Model Execution: Run multiple model instances on the same GPU simultaneously,
  with configurable GPU memory allocation per instance.
- Model Management: Hot-load, hot-unload, and version models without server downtime.
- Metrics: Exposes Prometheus-compatible metrics for request latency histograms, throughput,
  GPU utilization, and queue depth.

6.2 Performance Benchmarks (Triton v2.42, H100 SXM):

7. NEMO FRAMEWORK FOR GENERATIVE AI
================================================================================
NVIDIA NeMo is a scalable, cloud-native framework for building, customizing, and deploying
large generative AI models. It is designed to handle models with billions to trillions of
parameters using advanced distributed training techniques.

7.1 Supported Model Architectures:
- NeMo LLM: GPT-style autoregressive decoder models (NeMo GPT, Llama, Mistral, Mixtral)
- NeMo Multimodal: Vision-language models (NeVA — NVIDIA's LLaVA implementation)
- NeMo ASR: Automatic speech recognition (Conformer-CTC, Conformer-Transducer, Canary)
- NeMo TTS: Text-to-speech synthesis (FastPitch, HiFi-GAN, RADTTS)
- NeMo NLP: Token classification, text classification, question answering

7.2 Distributed Training Techniques in NeMo:
NeMo integrates NVIDIA Megatron-LM for large-scale distributed training:
- Data Parallelism (DP): Replicate the entire model on each GPU; split data across GPUs.
- Tensor Parallelism (TP): Split individual weight matrices across GPUs within a node.
  Requires high-bandwidth interconnects (NVLink). Typically TP=8 within a DGX node.
- Pipeline Parallelism (PP): Distribute model layers across GPUs in sequential stages.
  Introduces pipeline bubbles but reduces memory per GPU.
- Expert Parallelism (EP): For Mixture of Experts (MoE) models, distribute experts across
  GPUs. Combined with TP and PP for models like Mixtral 8x7B.
- Sequence Parallelism (SP): Split the sequence dimension across GPUs for LayerNorm and
  Dropout layers that cannot be tensor-parallelized.

Typical large-scale training configuration for a 175B parameter GPT-style model:
- Hardware: 128 DGX H100 nodes (1,024 H100 GPUs)
- Parallelism: TP=8, PP=16, DP=8 (8 * 16 * 8 = 1,024 GPUs)
- Global batch size: 2,048 sequences * 4,096 tokens = 8.4M tokens per step
- Estimated training time for 1 trillion tokens: ~12 days

7.3 Model Customization Techniques:
NeMo supports multiple customization approaches for adapting foundation models:
- Full Fine-Tuning (SFT): Update all model parameters on domain-specific data.
- Parameter-Efficient Fine-Tuning (PEFT):
  - LoRA (Low-Rank Adaptation): Insert trainable rank-decomposition matrices into attention
    and MLP layers. Typically trains only 0.1-1% of total parameters.
  - P-Tuning v2: Prepend trainable continuous prompt tokens to each transformer layer's
    input. No modification to the frozen model weights.
  - Adapters: Insert small trainable bottleneck layers between frozen transformer blocks.
- Reinforcement Learning from Human Feedback (RLHF):
  NeMo Aligner implements PPO (Proximal Policy Optimization), DPO (Direct Preference
  Optimization), and SteerLM for aligning LLMs with human preferences.
